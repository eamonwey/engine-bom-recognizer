## 1. P1：自动下标转换会把合法节点改指向其他零件

- 位置：engine_bom/assembly.py:19-24。
- 触发：3 行 BOM 为 A/B/C，合法根节点引用下标 1（B），另一个节点错误引用 3。
- 实际：只因为所有引用处于 1..3 且出现 3，程序把所有下标减 1；根节点从 B 变成 A，整棵树被接受。
- 原因：这组下标不一定表示统一的 1 基序号，也可能是正确的 0 基子集加一个越界错误。“整体减 1 是唯一解释”的假设不成立。当前函数还会原地修改调用方的 nodes。
- 建议：没有明确 index_base 或件号/序号交叉证据时保留原值并报错，让模型重试或人工确认；校验函数不应自行改写零件归属。手工保存路径同样调用此函数，也受影响。

## 2. P1：重试删除冲突节点即可被判为 validated

- 位置：engine_bom/assembly.py:245-250。
- 触发：第一轮得到完整树，螺钉展开数量 12、明细数量 11；第二轮省略螺钉节点。
- 实际：4 节点变成 3 节点，quantity_conflicts 变成空数组，inference_status=validated，未建立关系行增加为 [3]。
- 原因：“禁止删节点、降级关系”仅写在提示词，代码没有比较重试前后覆盖范围。第二轮直接覆盖 stash，只检查剩余节点的冲突。
- 影响：虽然仍显示未建立关系行，原来的数量错误及其图面证据不再作为 ERR-08 传给流水线。
- 建议：保存历史有效候选和冲突；节点消失、证据降级或用量变未知不能算作成功修复。只有可解释的重复节点合并等变更才可消除原冲突。

## 3. P1：少印数量会在对账前被当作结构错误，导致整棵树丢弃

- 位置：engine_bom/assembly.py:69-72。
- 触发：父件数量 1、图面支持每父件需要 3 个螺钉，但明细栏只印 2。
- 实际：validate_tree 因“每父用量超过明细总量”报错；模拟模型持续返回同一有证据树，重试结束得到 0 节点、needs_review，没有 quantity_conflicts。
- 原因：明细数量本来就是待核查对象，不能充当拒绝图面关系的硬约束。当前写法仅能处理部分数量矛盾，例如父件 3 × 每父用量 4 与明细 11，因为 4 不超过 11。
- 建议：将该条件交给 reconcile_quantities 输出 ERR-08，保留关系、原始数量和证据；结构校验仅拒绝非法类型、循环等结构问题。

## 4. P1：未知用量不计分，准确率和验收结论虚高

- 位置：engine_bom/evaluation/tree_metrics.py:97-104。
- 触发：两个父子关系均正确，标准用量分别为 2 和 3；预测为 2 和 null。
- 实际：qty_total=1、qty_accuracy=1.0，报告写“全部通过”。应有两个已标注用量接受评价，其中一个未识别。
- 原因：预测和标准用量分别过滤 null 后再 zip，缺失预测直接从分母消失；重复边的数量配对也会因此错位。
- 建议：按已匹配关系中有标注的用量作为分母，预测 null 应计为未正确识别，并单独报告缺失用量。若保留“仅已知预测准确率”，须明确命名并同时报告覆盖率，不能作为完整验收准确率。

## 5. P2：人工保存装配树未重新对账，丢失结构化冲突

- 位置：engine_bom/webapp.py:845-859；关联 static/extensions.js:3。
- 触发：保存前树含有 12 对 11 的 quantity_conflicts；前端只提交 nodes，保存接口重新 validate_tree。
- 实际：保存后 quantity_conflicts 字段消失、status=reviewed；对保存树重新运行 reconcile_quantities 仍得到 1 项冲突。
- 原因：人工保存没有接入今天新增的对账函数，也未同步更新 BOM.validation_issues。原流水线生成的旧文字提示可能继续保留，不代表结构化冲突仍存在；反过来人工修好后旧提示也可能继续存在。
- 建议：人工保存与自动推理使用同一套对账逻辑，保留未解决冲突、重新生成相应提示，并区分“已复核”与“数量一致”。

## 6. P2：重试 API 失败时丢弃已有有效候选及事件

- 位置：engine_bom/assembly.py:254-257。
- 触发：第一轮已经得到结构合法、带数量冲突的 4 节点树，第二轮 Provider 抛出超时错误。
- 实际：返回 provider_failed、nodes=[]、events=[]。与末轮 JSON 解析失败会回退 stash 的行为不同。
- 建议：异常分支同样保留最近有效树、冲突及此前事件；明确标记自纠未完成，不能把已有证据全部清空。

## 7. P2：多余根节点不影响验收“全部通过”结论

- 位置：engine_bom/evaluation/tree_metrics.py:38-40,193-215。
- 触发：标准为 A 根及两个子件；预测保留所有正确边，但额外增加一个 B 根。
- 实际：关系 F1=1.0，根列表从 [A] 变成 [A,B]，节点数从期望 3 变成 4，报告仍写“全部通过”。
- 原因：根单独记录但未参与关系计分，最终报告也不检查根列表、节点总数和期望深度是否一致。关系 F1 不含根可以是设计选择，但不能据此忽略完整树的验收条件。
- 建议：增加独立的根集合、节点数、深度判定，统一生成明确的通过/失败/待复核结果；仅所有必需条件满足时写“全部通过”。
